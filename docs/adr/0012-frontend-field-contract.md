# ADR-0012: 对外字段契约以后端视图对象为准，适配责任放前端

## 状态
已采纳（2026-10-28）

## 背景

一次全量排查发现，管理后台与用户端共有 6 处页面读取的字段名，与后端接口实际返回的字段名不一致，导致这些位置长期显示空白。另有约 16 处页面内联的「后端名 → 前端名」映射散落在各个页面里。

这些缺陷的共同特征：**不报错、不崩溃、构建通过、测试通过**，只是安静地显示空白。因此它们能从上线存活至今而无人察觉。

排查中确认差异分两类，性质完全不同：

1. **纯命名不一致**：后端返回 `coverImageUrl`，前端读 `coverImage`；后端给 `ownerId`，前端读 `userId`。
2. **后端结构上缺数据**：管理端黑名单接口直接返回实体，实体只含双方用户 ID，不含昵称与手机号——前端无论怎么写都拿不到。

同时发现，前端已有的字段适配（如共享物品、消息、商品）是**逐个手写**的，覆盖不全，于是页面只好再各补一遍。`index/index.vue` 里甚至重复实现了 `normalizeProduct` 已经做过的映射。

## 决策

**对外字段名以后端视图对象（VO）为准；字段适配的责任放在前端，并以「补全已有适配层」的方式实施，而非新建一层。**

具体规则：

1. **后端已返回值、前端读错名** → 改前端，读后端实际字段名。
2. **后端接口结构上缺该信息** → 改后端（补字段或补视图对象），不在前端拼凑。
3. **禁止前端字段别名**：不允许在前端为「后端没给的名字」写兼容写法（如 `a.followTime || a.createdAt`）。别名会让错误的字段名继续存在，把缺陷藏起来。
4. **适配层的落点分工**：
   - 全局响应拦截器只做**纯机械**映射（如分页壳 `records` → `list`）。
   - 具体的 `api/*.ts` 只做**带业务语义**的映射（如 `unitPrice` / `totalPrice` 取哪个）。
   - 页面**不再**承担字段改名职责。
5. **不引入工具链**（OpenAPI / Schema 代码生成）。当前规模下手写适配 + 后续的契约守卫足够。

## 理由

1. **后端为准，因为后端是数据的产生方**：字段的含义、是否存在，只有后端确定。前端「想要什么名字」不是约束条件。
2. **适配放前端，因为改动面小且可控**：后端视图对象已成形并被多处调用；改后端字段名会波及所有调用方，而前端加适配是局部改动。
3. **禁止别名，因为别名掩盖问题**：本次 6 处缺陷之所以长期存活，正是因为「两个都读」的写法让开发者以为已经兼容，实际后端根本不返回那个名字。
4. **复杂度留在它该在的地方**：全局拦截器处理所有接口都一样的机械转换；语义判断（该显示单价还是总价）只有业务代码知道，强塞进全局层会制造错误。
5. **不引入 Schema 工具链**：项目处于功能快速演进期，引入代码生成会带来构建复杂度和学习成本，收益在当前规模下不成比例。

## 后果

### 正面
- 字段名不一致会导致**明确的行为差异**（空白），而不再是静默错误。
- 新增页面时，字段适配有明确落点，不必再各写一遍。
- 后续可以加自动检查（前端读取的字段必须存在于后端返回类型），把这类缺陷拦在提交前。

### 负面
- 前端需要维护适配代码。视图对象改名时，前端必须同步跟进——这个约束由后续的契约守卫机械化兜底。
- 后端视图对象里会保留一些「前端专用」的字段（如为展示补的昵称、手机号）。这些字段属于**展示层需要**，放进视图对象是合理的，但不应写回实体。

## 备选方案

- **前端为准（后端改字段名去迎合前端）**：前端代码更干净，但要改动后端视图对象及其所有调用方，且「前端想要什么名字」并不是设计字段名的合理依据。否决。
- **引入 OpenAPI / JSON Schema 代码生成**：契约从此单一真源、可自动生成前端类型，是长期最优解。但需要引入工具链、改造构建流程，且当前接口数量与团队规模下收益不成比例。**列为未来可选项**，不作为当前决策。
- **在前端加统一别名表（把后端名映射成前端习惯的名字）**：改一处即可让所有页面工作。但会让前端继续使用后端不存在的名字，把问题藏得更深——正是本次缺陷的成因。否决。
- **允许各页面继续自写兜底**：零改动。但适配逻辑持续分散，同类缺陷会反复出现。否决。
