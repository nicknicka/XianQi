# ADR-0009: GitHub Actions CI 质量门禁

## 状态
已采纳（2026-10-27）

## 背景
ADR-0006 将第一阶段 CI 边界限定为“仅构建验证”，用于在缺少自动化测试和 lint 门禁时快速建立最低保障。随着后端测试、前端 ESLint 配置和只读 lint 自测落地，仅验证能否构建已经不足以拦截测试回归、真实 lint 违规或会改写源码的 lint 命令。

CI 仍没有确定的生产部署目标，也不应在质量门禁中执行发布动作。

## 决策
GitHub Actions CI 在构建和打包前执行质量门禁，但仍不自动部署：

1. **后端单元测试**：JDK 17 下运行全量 Maven 单元测试。
2. **后端集成测试与打包**：使用临时 MySQL 8.0 与 Redis 7 服务运行 Maven `verify`，覆盖集成测试并完成打包；任务结束后随 CI 环境销毁，不依赖持久化 Docker volume。
3. **管理后台门禁**：Node 20 下执行 `npm ci`、只读 `npm run lint` 和 `bash scripts/test-lint-gate.sh`，通过后才构建。
4. **移动 H5 门禁**：Node 20 下执行 `npm ci`、只读 `npm run lint` 和 `node --test test/lint-gate.test.mjs`，通过后才执行 H5 构建。
5. **产物保留**：上传后端 jar、admin `dist` 与 mobile H5 `dist` 作为 CI 构建产物，便于审查和手动取用。
6. **不自动部署**：本阶段不推送镜像、不连接服务器、不执行发布或回滚操作。

lint 门禁必须保持只读：普通 `npm run lint` 不得包含 `--fix`；需要自动修复时使用独立的 `lint:fix` 入口，并由门禁自测验证 lint 执行前后的项目源码与配置快照一致。

## 理由
1. **测试应在合并前反馈**：后端单元测试和依赖 MySQL/Redis 的集成测试能验证构建无法覆盖的行为契约。
2. **lint 是质量门禁而非格式化任务**：只读执行可以发现真实违规，同时避免 CI 意外改写工作区。
3. **门禁自测保护门禁本身**：测试脚本验证 ESLint 配置、文件覆盖、红绿行为和 CI 顺序，降低门禁被误删或退化成自动修复的风险。
4. **临时服务保证隔离性**：每个 CI job 使用独立 MySQL/Redis 容器，测试数据不进入本地或生产持久化卷。
5. **保留发布边界**：上传产物支持检查和手动部署，但在部署目标与发布流程明确前不引入 CD。

## 后果
### 正面
- PR 在构建前获得后端测试、前端 lint 和门禁自测反馈。
- 集成测试在接近真实依赖的隔离环境中运行。
- CI 产物可追溯，但不会触发未经授权的环境变更。
- 只读 lint 的约束由自动化测试固定下来。

### 负面
- CI 时间比 ADR-0006 的仅构建方案更长。
- MySQL/Redis 集成测试要求测试配置与 CI 服务参数保持一致。
- 前端历史代码需要通过精确的 ESLint 配置或后续专项治理维持门禁可执行。

## 与 ADR-0006 的关系
本 ADR 取代 ADR-0006 的“仅构建”边界。构建仍是必需步骤，但不再是充分条件；现在必须先通过后端测试、前端只读 lint 与 lint 门禁自测，才允许构建、打包和上传产物。“不自动部署”的边界继续保持不变。
