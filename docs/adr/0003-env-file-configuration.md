# ADR-0003: 环境变量 + .env 文件管理配置

## 状态
已采纳

## 背景
原项目存在以下问题：
1. 敏感信息（API Key、数据库密码等）硬编码在配置文件中，并提交到了 Git
2. 三个项目各有各的配置文件，配置分散且可能不一致
3. 切换环境（开发/测试/生产）需要修改多处配置

## 决策
采用 `.env` 文件 + 环境变量的方式管理所有配置：

1. **根目录 `.env.example`**：配置模板，包含所有可配置项和默认值，提交到 Git
2. **根目录 `.env`**：实际使用的配置文件，加入 `.gitignore`，不提交
3. **后端 application.yml**：所有敏感/可变配置改为读取环境变量，带默认值
4. **前端 .env.production**：API 地址改为相对路径，其他可变配置读取构建时环境变量
5. **docker-compose.yml**：通过 `${VAR:-default}` 语法从 `.env` 读取变量

### 配置分类
- **基础设施配置**：数据库、Redis 连接信息
- **安全配置**：JWT 密钥、密码盐等
- **第三方服务**：OSS、短信、AI、支付、地图等
- **业务配置**：上传大小限制、订单超时时间等
- **部署配置**：端口、域名、profile 等

## 理由
1. **安全**：敏感信息不提交到 Git，避免泄露
2. **统一**：所有配置在一个文件里，一目了然
3. **灵活**：切换环境只需要改 `.env` 文件
4. **标准**：Docker Compose 原生支持 .env 文件
5. **文档化**：.env.example 本身就是配置文档

## 后果
### 正面
- 安全性大幅提升
- 部署更灵活，一份代码适配多种环境
- 新人上手更容易，看 .env.example 就知道要配什么

### 负面
- 新增配置需要同时改 .env.example 和 application.yml/docker-compose.yml
- 本地开发需要先复制 .env.example 为 .env
